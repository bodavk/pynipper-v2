# Release-dependent insecure defaults (SC-044 reference)

Researched **2026-09-26 to 2026-09-28** from vendor documentation. Implementation pass **2026-09-29**: 84 of the 109 primary-vendor rows are now `impl` (plus 4 secondary-family rows); tests in `tests/test_sc044_defaults_{ios,asa,fortios,f5,gaia,secondary}.py`. This is the basis for implementing [SC-044](SECURITY_COVERAGE_TASKS.md#sc-044) and for reviewing absence-based rules elsewhere in the backlog. It is a research register, not a list of implemented checks: the "Status" column says which rows already have code.

## Why this exists

Most exports omit settings that are at their default value (IOS `show running-config`, ASA `show running-config`, FortiOS `show`, BIG-IP SCF/`tmsh list`). A missing line therefore means "whatever this release does by default". The project rule is unchanged: **an absent setting may only produce a finding when a vendor source documents the default for the exported release** (`FindingBasis.DOCUMENTED_DEFAULT`). Everything else stays unknown or is reported only when explicit.

## How to use the tables

- **ID** is a stable reference for tasks and code comments (for example `# SC-044 ASA-07`).
- **Auditor decision** is the proposed logic. "Explicit only" means the default is secure or unknown, so a finding needs an explicit weak value.
- **Rule** names an existing rule (plain) or a proposed one (*italic*).
- **Conf** is the evidence quality:
  - **V**: verbatim vendor text (page read in full, for example through the browser pane).
  - **S**: vendor page read through a summarising fetch. Re-read the page before the rule ships.
  - **C**: CIS/DISA/Tenable benchmark text or another secondary source. Never gate on C alone without a vendor confirmation, unless the row says so.
- **Status**: `impl` = already implemented with this logic, `partial` = implemented for explicit values only, `todo` = not implemented.
- Severities are suggestions; final severity follows the proven state and exposure.
- Where the vendor's own documents disagree, the row is marked **CONFLICT** and the more specific source (release notes, bug notes, K-articles) wins, as stated in the row.

## Version extraction

| Family | Where the release comes from | Granularity | Notes |
|---|---|---|---|
| IOS / IOS-XE | `version X.Y` line | Train only (`12.1`, `15.2`, `17.9`) | Gates inside a train (12.1(5), 15.4(3)M4, 16.6.4) need `--software-version`; otherwise report "possible" at reduced confidence or skip. IOS-XE is `16.x`/`17.x`/`26.x`. |
| ASA / PIX | `ASA Version 9.16(4)` / `PIX Version 6.3(5)` header | Exact | Parse `(\d+)\.(\d+)\((\d+)(?:\.(\d+))?\)(\S*)`. Multi-train gates (for example 9.1(7)/9.4(3)/9.5(3)/9.6(1)) need a per-train minimum map. |
| FortiOS | `#config-version=FGT60F-7.2.5-FW-build…` | Exact | CLI reference pages for 6.2.x and 6.4.0 have no Default cells; the oldest verified release is **6.4.14**. Document IDs in docs.fortinet.com URLs change per release. |
| BIG-IP | `#TMSH-VERSION: 16.1.5` | Exact | Gates at 11.5.0, 11.5.3, 11.6.0, 12.0.0, 13.1.0, 14.0.0. Profiles inherit through `defaults-from`; resolve the parent before applying defaults. |
| Gaia | not in `show configuration` (`# Language version` is the Clish syntax version) | Lower bound only | `set ssh server …` ⇒ ≥ R81.20; `protocol` on `add syslog log-remote-address` ⇒ ≥ R81.20; `set cluster member ccpenc` ⇒ ≥ R80.30. Word such findings "at least Rxx". |
| Check Point FW1 | objects.C gateway `version` attribute (field not yet verified on a sample) | Per gateway | Needed for the R80.10 implicit-cleanup gate and VPN community defaults. |

Upgrades: once an export is written by a newer release, an **absent** value means the newer default. An old default only survives an upgrade if it was saved explicitly, so always evaluate explicit values first and interpret absence against the header version.
