1. Clear-text HTTP management service enabled

Management access exposure cisco.ios.http.cleartext_service

What was found

The IOS HTTP management server is explicitly enabled.

Why it matters

Administrative credentials and sessions can be exposed to interception or modification.

In plain terms: The device can be managed over an unencrypted protocol such as Telnet or plain HTTP. Everything typed or sent in such a session, including administrator passwords, crosses the network readable by anyone on the path.

How it could be abused

An attacker with access to the management traffic path can observe or alter clear-text HTTP traffic.

Example: An attacker who has compromised any host on the same network segment (or a switch or Wi-Fi link on the way) captures traffic while an administrator logs in, reads the password from the capture, and later logs in as that administrator.

How to fix

Disable it with 'no ip http server' and use HTTPS or SSH for remote administration.

Before closing this finding: Check whether management traffic is confined to an isolated management network or VPN, and whether the clear-text service is additionally restricted to specific source addresses. Those reduce, but do not remove, the exposure.

2. HTTP management access is unrestricted

Management access exposure cisco.ios.http.access_restriction

What was found

The enabled HTTP server has no effective 'ip http access-class' restriction.

Why it matters

Untrusted networks may be able to reach the device management service.

In plain terms: The device's management interfaces (SSH, web GUI, API) accept connections from any address, or from an untrusted/external network, instead of only from administrator workstations or a management network.

How it could be abused

An attacker only needs network reachability to attempt authentication or exploit the HTTP service.

Example: The login page of the firewall is reachable from the internet. Attackers try common and leaked passwords against it around the clock, and when a new vulnerability in the management service is published, they can exploit it before the device is patched.

How to fix

Restrict management sources with 'ip http access-class <ACL>' or disable HTTP.

Before closing this finding: Check for an upstream control that already limits access (management VLAN, VPN, separate out-of-band network), and confirm that strong authentication, lockout and logging are in place for the exposed service.

3. SSH protocol version 2 is not enforced

Management encryption and certificates cisco.ios.ssh.protocol_version

What was found

The reachable SSH service uses version '1'.

Why it matters

SSHv1 has fundamental protocol weaknesses and permits downgrade exposure where compatibility mode is allowed.

In plain terms: The encrypted management connection (SSH or HTTPS) still allows outdated protocol versions or algorithms that are known to be weak.

How it could be abused

An on-path attacker may be able to exploit SSHv1 weaknesses or force use of the legacy protocol.

Example: An attacker positioned on the network path forces or waits for a connection that uses the weak option, then attacks it offline or tampers with it. Old options also widen exposure to published protocol attacks.

How to fix

Enforce SSHv2 with 'ip ssh version 2'.

Before closing this finding: Confirm which clients (old monitoring or automation tools) still need legacy options, and plan to upgrade them rather than keep weak algorithms enabled.

4. Centralized AAA is not enabled

Administrator authentication cisco.ios.aaa.new_model

What was found

The effective configuration does not enable 'aaa new-model'.

Why it matters

Authentication, authorization, and accounting policy may be inconsistent and locally controlled.

In plain terms: A way to log in to the device is not protected by a proper authentication method: it may allow an empty password, a direct root login, a method that always succeeds, or point to an authentication server that is not actually defined.

How it could be abused

An attacker with management-plane or configuration access may exploit this weakness.

Example: Someone with network (or physical console) access connects to the line or service and gets a management prompt without knowing a valid personal password, or by using a shared built-in account that is never locked or audited per person.

How to fix

Enable AAA new-model and define a tested local fallback before applying it to management lines.

Before closing this finding: Check whether physical access to the console is controlled and whether the path is reachable at all, and confirm with a test login that the intended authentication method is actually used.

10. Local credential uses weak storage

Stored credentials and password policy cisco.ios.credentials.local_storage

What was found

User 'admin' uses 'password' storage type '0', classified as 'plaintext' under credential policy 'pynipper-v2/default-v1'; the separate blocklist comparison was not evaluated against a supplied credential blocklist. The credential is redacted.

Why it matters

Plaintext, reversible, or legacy hashes are more readily recovered from a configuration disclosure.

In plain terms: A password or key is stored in the configuration in plain text or with a weak, easily reversible encoding (for example Cisco type 7 or MD5-based hashes).

How it could be abused

An attacker with management-plane or configuration access may exploit this weakness.

Example: A configuration backup is copied to a file share, ticket or email. Anyone who gets that file can read or quickly crack the password and log in to this device, and to any other system where the same password is reused.

How to fix

Use a supported strong secret algorithm and migrate administrative authentication to AAA.

Before closing this finding: Check where configuration backups are stored and who can read them, and rotate any credential that has been stored weakly.
