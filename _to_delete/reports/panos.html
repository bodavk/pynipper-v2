1. Unrestricted security policy rule

Firewall and access policy paloalto.panos.policy.broad_allow

What was found

Enabled rule 'ANY-ALLOW' at position 1 in 'vsys1' allows any zone, source, user, destination, application, service, and category without a schedule restriction.

Why it matters

The rule can bypass intended network and application segmentation.

A traffic rule (or the default action for unmatched traffic) allows much more than a business need usually requires, such as any source to any destination on any service. The firewall then no longer separates the networks on either side of it.

How it could be abused

Any matching source can reach any routable destination and application permitted by surrounding infrastructure.

Example: Malware on one laptop in a user network scans the network and reaches a database or management interface in a server network, because the broad rule lets that traffic through. The attacker never has to defeat the firewall itself.

How to fix

Replace wildcard match dimensions with explicit zones, addresses, users, applications, and application-default service where appropriate.

Before closing this finding: Confirm who owns the rule and which flows it must carry, then replace it with explicit sources, destinations and services. Until then, make sure the traffic it matches is logged and inspected (see the related areas), so misuse would at least be visible.

2. Clear-text management service is exposed

Management access exposure paloalto.panos.management.http

What was found

Attached management profile enables HTTP on interface 'ethernet1/1' in scope 'vsys1' and zone 'untrust'.

Why it matters

Administrative credentials and sessions can be disclosed or altered in transit.

The device can be managed over an unencrypted protocol such as Telnet or plain HTTP. Everything typed or sent in such a session, including administrator passwords, crosses the network readable by anyone on the path.

How it could be abused

An attacker with management-path reachability can intercept or attempt access to the clear-text service.

Example: An attacker who has compromised any host on the same network segment (or a switch or Wi-Fi link on the way) captures traffic while an administrator logs in, reads the password from the capture, and later logs in as that administrator.

How to fix

Disable HTTP in the attached Interface Management profile and use SSH or HTTPS.

Before closing this finding: Check whether management traffic is confined to an isolated management network or VPN, and whether the clear-text service is additionally restricted to specific source addresses. Those reduce, but do not remove, the exposure.

3. Management service lacks permitted-IP restrictions

Management access exposure paloalto.panos.management.unrestricted_secure_service

What was found

HTTPS/SSH is enabled on 'ethernet1/1' in scope 'vsys1' and zone 'untrust' without permitted IP addresses.

Why it matters

The management plane is reachable from every source allowed to reach the interface.

The device's management interfaces (SSH, web GUI, API) accept connections from any address, or from an untrusted/external network, instead of only from administrator workstations or a management network.

How it could be abused

Any reachable host can probe the service or attempt authentication.

Example: The login page of the firewall is reachable from the internet. Attackers try common and leaked passwords against it around the clock, and when a new vulnerability in the management service is published, they can exploit it before the device is patched.

How to fix

Add explicit IPv4/IPv6 Permitted IP Addresses or remove management access from the untrusted interface.

Before closing this finding: Check for an upstream control that already limits access (management VLAN, VPN, separate out-of-band network), and confirm that strong authentication, lockout and logging are in place for the exposed service.

4. Allow rule has no security profile attachment

Threat inspection and security updates paloalto.panos.policy.security_profiles

What was found

Enabled allow rule 'ANY-ALLOW' in 'vsys1' has no profile group or individual security profiles.

Why it matters

Permitted traffic may bypass threat, malware, URL, file, and data inspection controls.

Traffic that the firewall allows is not fully checked for known attacks or malware, or the signatures used for that check are not kept up to date.

How it could be abused

An attacker can deliver malicious content through traffic permitted by the uninspected rule.

Example: An allowed web or file-transfer connection carries a known exploit or malware sample. Because intrusion prevention or antivirus is not attached to the rule (or only alerts instead of blocking, or runs on old signatures), the attack passes through unchanged.

How to fix

Attach the organization's approved Security Profile Group or explicit profiles to the allow rule.

Before closing this finding: Confirm the subscriptions are licensed and current on the device, and check whether another control (proxy, endpoint protection, upstream IPS) inspects the same traffic.

6. Management SSH service profile is not applied

Management encryption and certificates paloalto.panos.admin.ssh_profile_missing

What was found

SSH management is enabled in device scope 'localhost.localdomain' without an applied management SSH service profile.

Why it matters

The management SSH server can advertise the full default algorithm set instead of an explicitly restricted policy.

The encrypted management connection (SSH or HTTPS) still allows outdated protocol versions or algorithms that are known to be weak.

How it could be abused

A reachable SSH client can negotiate any algorithm that remains available in the default server set.

Example: An attacker positioned on the network path forces or waits for a connection that uses the weak option, then attacks it offline or tampers with it. Old options also widen exposure to published protocol attacks.

How to fix

Create, apply, and activate a management SSH service profile containing only approved algorithms.

Before closing this finding: Confirm which clients (old monitoring or automation tools) still need legacy options, and plan to upgrade them rather than keep weak algorithms enabled.

Evidence in the configuration

LineFileConfiguration
— vulnerable.xml localhost.localdomain: management SSH profile absent (no single source line, e.g. a missing setting or a summarized/redacted value)

Also check

  • Management access exposure: High Clear-text management service is exposed, High Management service lacks permitted-IP restrictions
  • Administrator authentication: Medium Administrators use local-only authentication
Technical background and references

Examples include SSH version 1, 3DES/CBC ciphers, SHA-1/MD5 MACs, small Diffie-Hellman groups, TLS 1.0/1.1 and static-RSA key exchange. Modern clients do not need these; keeping them only helps an attacker. The tool reports explicitly configured weak options and does not guess vendor defaults.

9. Allow rule lacks effective centralized log forwarding

Logging, accounting and change audit paloalto.panos.policy.log_forwarding

What was found

Enabled allow rule 'ANY-ALLOW' in 'vsys1' references 'no log-forwarding profile', which does not resolve to a same-scope profile with a syslog destination.

Why it matters

Traffic and threat events may remain only in limited local storage and be unavailable to central monitoring.

Traffic allowed by this rule is not logged, or its logs never reach a central log server. If the rule is misused, there is no record of it.

How it could be abused

Reduced centralized telemetry can delay detection and investigation of malicious traffic.

Example: An attacker uses an allowed path to copy data out of the network over several days. During incident response nobody can tell which hosts talked to each other, when, or how much data left, because the firewall kept no session records for that rule.

How to fix

Attach a same-vsys Log Forwarding profile with an active syslog destination and enable session-end logging.

Before closing this finding: Check that the rule's traffic is logged elsewhere (for example on a downstream proxy or flow collector) and that the central log destination is configured and reachable.

Evidence in the configuration

LineFileConfiguration
Line 13 vulnerable.xml localhost.localdomain/vsys1/rulebase: security rule 1 ANY-ALLOW

Also check

  • Time synchronization: Low No NTP servers are configured
  • Firewall and access policy: Critical Unrestricted security policy rule
Technical background and references

Session logs are a primary source for detection and forensics. Logging at session end records duration and byte counts; forwarding to a central collector protects the records if the firewall itself is compromised or its local disk rotates.
